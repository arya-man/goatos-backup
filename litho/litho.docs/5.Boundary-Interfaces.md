# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### backend/cmd/api

**Description**: Main entry point for the Go backend HTTP API server. Bootstraps configuration, starts the HTTP server, sets up signal handling (SIGINT, SIGTERM) for graceful shutdown, and flushes telemetry/observability data before exit.

**Source File**: `./backend/cmd/api/main.go`

**Options**:

- `PORT`(env_var): optional - HTTP listen port for the API server (read from environment). (default: `8080`)
- `DATABASE_URL`(env_var): required - PostgreSQL connection string used by the bootstrap/config module.

**Usage Examples**:

```bash
go run ./backend/cmd/api
```

### backend/cmd/migrate

**Description**: Database migration CLI utility that connects to PostgreSQL and applies/reverts/lists SQL migration files, validating integrity via SHA256 hashing and tracking applied migrations.

**Source File**: `./backend/cmd/migrate/main.go`

**Options**:

- `--migrations-dir`(string): optional - Directory containing SQL migration files. (default: `./migrations/postgres`)
- `--database-url`(string): required - PostgreSQL connection URL to apply migrations against.

**Usage Examples**:

```bash
go run ./backend/cmd/migrate --database-url=postgres://... --migrations-dir=./backend/migrations/postgres
```

### backend/cmd/analytics-rollup

**Description**: Batch job (intended for Cloud Scheduler on Cloud Run) that runs once daily to aggregate GA4/Crashlytics BigQuery exports and upsert rollups into Postgres analytics tables (funnel_daily, journey_daily, engagement_daily, crash_daily).

**Source File**: `./backend/cmd/analytics-rollup/main.go`

**Options**:

- `BIGQUERY_PROJECT`(env_var): required - GCP project ID for BigQuery source datasets.
- `DATABASE_URL`(env_var): required - Postgres connection string for rollup upserts.

**Usage Examples**:

```bash
go run ./backend/cmd/analytics-rollup
```

### backend/cmd/outbox-dlq

**Description**: CLI tool for inspecting and processing dead-lettered outbox events that require manual intervention or retry.

**Source File**: `./backend/cmd/outbox-dlq/main.go`

**Options**:

- `--dry-run`(bool): optional - If set, only reports DLQ events without mutating state. (default: `false`)

**Usage Examples**:

```bash
go run ./backend/cmd/outbox-dlq --dry-run
```

### backend/cmd/sop-review-fanout-retry

**Description**: Retry utility that queries SOP reviews (accepted/reworked) with incomplete post-commit vaccination fanouts and re-executes the fanout logic durably.

**Source File**: `./backend/cmd/sop-review-fanout-retry/main.go`

**Options**:

- `--batch-size`(int): optional - Number of SOP review records to process per run. (default: `100`)

**Usage Examples**:

```bash
go run ./backend/cmd/sop-review-fanout-retry
```

### tools/ceo-ai/eval

**Description**: Regression evaluation tool for the CEO AI assistant. Loads a golden question set, calls the assistant/oracle, scores answers deterministically, and emits JSON/HTML reports.

**Source File**: `./tools/ceo-ai/eval/main.go`

**Arguments**:

- `questions-file` (string): optional - Path to the golden question dataset. (default: `golden/questions.json`)

**Options**:

- `--output, -o`(string): optional - Output directory for JSON/HTML evaluation reports. (default: `./report`)

**Usage Examples**:

```bash
go run ./tools/ceo-ai/eval --output=./report
```

### tools/deploy/slack-stg-deploy-bot

**Description**: Deployment bot server that listens for Slack interactive webhook events and Cloud Build notifications to orchestrate staging deployment triggers.

**Source File**: `./tools/deploy/slack-stg-deploy-bot/main.go`

**Options**:

- `SLACK_SIGNING_SECRET`(env_var): required - Secret used to verify HMAC-SHA256 signatures on incoming Slack requests.
- `GCP_PROJECT`(env_var): required - Google Cloud project used for Cloud Build trigger API calls.
- `ALLOWED_USERS`(env_var): optional - Comma-separated allowlist of Slack user IDs permitted to trigger deployments.

**Usage Examples**:

```bash
go run ./tools/deploy/slack-stg-deploy-bot
```

## API Interfaces

### GET/POST /api/counts/*

**Description**: Herd register read-model API exposing count analytics, breakdown, and herd query endpoints. Delegates to counts app service after auth/authorization middleware.

**Source File**: `./backend/internal/counts/adapters/http/handler.go`

**Request Format**: Query parameters and/or JSON body

**Response Format**: JSON

**Authentication**: Firebase-based auth middleware with role/permission checks

### GET/POST/PUT /api/procurement/feed-purchases

**Description**: CRUD endpoints for managing feed purchase records, including pagination and filtering support, backed by the FeedPurchaseService application layer.

**Source File**: `./backend/internal/procurement/adapters/http/handler.go`

**Request Format**: JSON

**Response Format**: JSON

**Authentication**: Middleware-based auth/authorization

### GET/POST /api/verification/queue

**Description**: Verification queue endpoints supporting sorting, filtering, and permission-checked access to items pending QA/verification review.

**Source File**: `./backend/internal/verification/adapters/http/handler.go`

**Request Format**: Query parameters and/or JSON body

**Response Format**: JSON

**Authentication**: Permissions middleware

### POST /api/ceo-ai/ask

**Description**: Primary AI assistant endpoint. Accepts a natural-language question, orchestrates decomposition/tool execution/synthesis, and returns a grounded, safety-reviewed answer.

**Source File**: `./backend/internal/ceoai/app/orchestrator.go`

**Request Format**: JSON (AskRequest: question, conversation context)

**Response Format**: JSON (Answer with grounding metadata)

**Authentication**: Identity + rate-limit + budget checks via safety Layer

### POST / (Slack interaction webhook)

**Description**: Webhook handler receiving Slack interactive component payloads and Cloud Build notifications; verifies HMAC signature and authorizes user before triggering Cloud Build deployment pipelines.

**Source File**: `./tools/deploy/slack-stg-deploy-bot/main.go`

**Request Format**: Slack payload (form-encoded/JSON) or Cloud Build notification JSON

**Response Format**: JSON / Slack response payload

**Authentication**: HMAC-SHA256 signature verification + user allowlist

### GET /api/*/bootstrap, /api/*/analytics

**Description**: Server-only API client layer (admin-web) providing type-safe wrappers over generated OpenAPI endpoints for bootstrap data, health/herd/weight analytics, and vaccination passport queries; mints local-dev bearer tokens from Firebase identity.

**Source File**: `./apps/admin-web/lib/api/server.ts`

**Request Format**: N/A (internal server function calls)

**Response Format**: Typed JSON envelopes (ErrorEnvelope, AdminWebBootstrapResponse, HealthAnalyticsResponse, etc.)

**Authentication**: Firebase ID token / local dev bearer token minting

## Integration Suggestions

### CLI/Environment Configuration

Standardize all backend cmd/* binaries to consistently support both environment variables and CLI flags for critical configuration (DATABASE_URL, GCP project, log level), and document them centrally to reduce onboarding friction for new batch jobs.

**Example Code**:

```
flag.StringVar(&cfg.DatabaseURL, "database-url", os.Getenv("DATABASE_URL"), "Postgres connection string")
```

**Best Practices**:

- Use a shared internal/platform config loader across all cmd/* entry points
- Fail fast with clear error messages when required env vars/flags are missing
- Support --dry-run flags on all destructive/retry CLI tools (migrate, outbox-dlq, sop-review-fanout-retry)

### HTTP API Gateway

Consolidate the many bounded-context HTTP handlers (counts, procurement, verification, feed, health, vaccination, etc.) behind a documented OpenAPI contract to enable consistent client generation (as already done via packages/api-client) and reduce endpoint drift.

**Example Code**:

```
router.Handle("/api/counts", authMiddleware(permissionsMiddleware(countsHandler)))
```

**Best Practices**:

- Generate OpenAPI specs from contracts/openapi and keep handler.go implementations in sync
- Apply consistent middleware chain (auth, permissions, logging) across all domain HTTP handlers
- Version API endpoints to support backward compatibility during bounded-context evolution

### Webhook Security

Apply the HMAC-SHA256 signature verification pattern used in slack-stg-deploy-bot to any other external webhook integrations (e.g., future Cloud Build, GitHub, or notification provider webhooks) to prevent spoofed requests.

**Example Code**:

```
if !hmac.Equal(computedSig, providedSig) { http.Error(w, "invalid signature", http.StatusUnauthorized); return }
```

**Best Practices**:

- Always verify signatures before parsing payload
- Use constant-time comparison for HMAC verification
- Maintain an explicit allowlist for privileged webhook actions

### Scheduled Batch Job Orchestration

Formalize analytics-rollup and other periodic cmd/* jobs (partition-maintainer, obligation-sweeper, idempotency-key-sweeper) under a common Cloud Scheduler + Cloud Run job pattern with shared retry/backoff and alerting via cost-alert-bridge.

**Example Code**:

```
gcloud scheduler jobs create http analytics-rollup --schedule="0 2 * * *" --uri=<cloud-run-url>
```

**Best Practices**:

- Emit structured logs/metrics for job success/failure to Grafana/observability stack
- Use idempotent upsert logic to safely handle re-runs
- Centralize scheduling configuration in infra/envs/*
