# Shared Contracts & Developer Tooling Domain

## 1. Purpose and Role in the Platform

The **Shared Contracts & Developer Tooling Domain** is GoatOS's cross-cutting infrastructure layer for keeping a Go backend (45+ bounded contexts), four client applications (admin-web, goatos-android, operator-mobile, investor-web-shadow), and an OLAP analytics layer synchronized on *what the data looks like* and *how engineers safely change it*. It does not implement business logic itself; instead, it provides the **contracts** (schema-first definitions of APIs, events, and forms) and the **tooling** (code generators, validators, CI guards, and AI-agent documentation sync) that every other domain depends on to interoperate correctly.

Structurally, the domain spans three physical locations in the monorepo:

| Location | Responsibility |
|---|---|
| `./packages/*` | TypeScript-first shared client libraries consumed by web and mobile apps |
| `./contracts/*` | Canonical OpenAPI/JSON Schema specifications and validated example payloads |
| `./tools/*` | CI automation, contract validation, data repair, and developer/AI tooling scripts |

Because GoatOS has no separate microservices boundary — it is a modular monolith with many independently evolving domains and four separate frontend surfaces — this domain functions as the **anti-drift layer**: it converts backend Go contracts into type-safe TypeScript artifacts, enforces `additionalProperties: false` on audit-critical schemas, and gates CI merges on contract/schema conformance so that a change in one bounded context cannot silently break a consumer elsewhere in the monorepo.

## 2. Shared Client Packages (`./packages`)

All packages under `./packages` are private, ES-module (`"type": "module"`) TypeScript workspace packages. Each declares `main`/`types` pointing directly at its `src/index.ts` (no build step is required for consumption inside the monorepo — TypeScript project references / bundlers resolve the source directly). This keeps the developer loop tight: editing a shared package takes effect immediately in any consumer without an intermediate compile/publish cycle.

```
packages/
├── api-client/            → generated, typed REST clients (app/admin/analytics)
├── device-client/         → pure device-registration gate logic
├── media-client/          → pure proof-upload state machine
├── forms-dsl/             → SOP Form DSL types + evaluateForm()
└── mobile-forms-runner/   → maps forms-dsl output to renderable UI models
```

### 2.1 `@goatos/api-client` — Generated, Type-Safe API Clients

This is the most heavily engineered package in the domain. It solves the classic contract-drift problem — "does the frontend's understanding of an endpoint still match the backend?" — by **never hand-writing the request/response types**. Instead:

1. **Code generation pipeline.** The package's `generate` npm script invokes `openapi-typescript` (pinned at version `7.13.0`) three times, once per OpenAPI spec:
   ```
   openapi-typescript ../../contracts/openapi/app-api.yaml      -o src/generated/app-api.ts
   openapi-typescript ../../contracts/openapi/admin-api.yaml    -o src/generated/admin-api.ts
   openapi-typescript ../../contracts/openapi/analytics-api.yaml -o src/generated/analytics-api.ts
   ```
   Each output file is a large, non-editable artifact (the `app-api.ts` file alone is ~27,500 lines / 1.36 MB, `admin-api.ts` is comparably large) containing a `paths` interface (per-route request/response/parameter shapes) and a `components` interface (schema definitions), generated verbatim from the YAML contract. Every generated file begins with the header comment `"This file was auto-generated by openapi-typescript. Do not make direct changes to the file."`
   
2. **Drift detection via `check` script.** The companion `check` script runs `generate` and then `git diff --exit-code -- src/generated`. If regenerating the types from the current `.yaml` contracts produces *any* diff, the script fails — meaning a contract change was made without regenerating clients, or a generated file was hand-edited. This is the primary automated anti-drift gate for the API surface.

3. **Hand-written runtime layer (`src/index.ts`).** On top of the generated (pure-type) files, `index.ts` adds the actual runtime behavior:
   - `ApiFamily` (`"app" | "admin" | "analytics"`) and a `GoatOSApiPaths` map tying each family to its generated `paths` type.
   - `GoatOSApiError` — a typed `Error` subclass carrying the HTTP `status` and parsed response `body`, thrown whenever `response.ok` is false (excluding `304 Not Modified`, which is treated as a valid cache-hit response).
   - `createGoatOSClient<Paths>(options)` — a generic factory returning an object with `request()` and `requestWithResponse()`. Its key design details:
     - **Query serialization contract**: array-valued query parameters are serialized as *repeated* parameters (`?feed_item=A&feed_item=B`) via `URLSearchParams.append`, deliberately avoiding a naive `String(array)` comma-join. The code comments explicitly document why: a Go backend reading `r.URL.Query()["feed_item"]` would otherwise receive one literal value `"a,b"` that matches nothing — a silent, hard-to-diagnose failure mode this client is built to avoid.
     - **Pluggable trace propagation**: an optional `getTraceHeaders()` hook lets callers (e.g., admin-web forwarding a Faro/OTel `traceparent` header from the browser→Next.js hop) attach distributed-tracing headers without coupling the client to any specific tracing SDK.
     - **Tenant/Auth headers**: `tenantId` is automatically attached via `X-GoatOS-Tenant-ID` (exported as `TENANT_CONTEXT_HEADER`), and `bearerToken` via a standard `Authorization: Bearer` header.
     - **`parseResponse()`**: a shared response-parsing helper — `204` and empty bodies become `null`; `application/json` bodies are parsed; anything else is returned as raw text.
   - Three thin factory wrappers — `createAppApiClient`, `createAdminApiClient`, `createAnalyticsApiClient` — each bind `createGoatOSClient` to one of the three path families, so consumers get full compile-time autocomplete/type-checking against the exact OpenAPI-declared routes.
   - Shared constants `TENANT_CONTEXT_HEADER` and `AUTH_SESSION_USER_AGENT_HEADER` are additionally exported from a small hand-written `constants.js`/`constants.d.ts` pair (kept outside the generated tree) and re-exported via a dedicated `./constants` package export in `package.json`, so non-TypeScript or partial consumers can import the header names without pulling in the full generated API surface.

This design cleanly separates **what never changes by hand** (generated types) from **what is intentionally hand-maintained** (the transport/runtime concerns: errors, headers, tracing, query encoding) — a pattern that scales well as new OpenAPI operations are added without touching runtime code.

### 2.2 `@goatos/forms-dsl` — SOP Form Domain-Specific Language

`forms-dsl` defines the canonical, versioned data model for **Standard Operating Procedure (SOP) forms** used across field-capture workflows (feed distribution, preventive care, vaccination execution, pen visits, etc.). Its exported types form a small, closed vocabulary:

- **`SOPFieldType`** — exactly ten allowed field kinds: `text`, `number`, `date_time`, `select`, `multiselect`, `goat_lookup`, `animal_id_scan`, `location_picker`, `photo_proof`, `video_proof`. This closed set intentionally couples form authoring to the concrete capabilities the mobile capture UI can render (e.g., RFID-driven `animal_id_scan`, camera-driven `photo_proof`/`video_proof`).
- **`SOPFormDSL`** — the form document itself: `schema_version` pinned to the literal `"goatos.sop-form.v1"`, `sop_code`, `title`, an optional `repeat_for_each_goat` flag, an array of `SOPField`s, optional `SOPRule`s, and an optional `workflow` graph (`nodes`/`edges`) describing state transitions (e.g., `operator_execution → proof_verification → approval`).
- **`SOPRule`** — a small rule engine vocabulary: `visible_if`, `required_if`, `block_submission_if`, `proof_required_if`, `validation_rule`, each keyed off a `when` clause (`field`, `operator` ∈ `{equals, not_equals, empty, not_empty, in}`, `value`).
- **`ProofReference`** — the shape of an attached proof artifact, tracking `proof_type` (`photo|video|attachment`), `subject_type` (`batch|goat|shed|task|other`), and an `upload_state` lifecycle (`pending|uploading|completed|failed`) — the same lifecycle vocabulary shared with `media-client`.
- **`evaluateForm(dsl, answers, proofRefs, proofRequired, verifyBeforeApply)`** — the pure evaluation function at the heart of the package. It walks every field, flags missing-but-required answers as `required` errors, checks whether at least one `completed` proof exists when `proofRequired` is set, and computes a `workflow_path` and `final_state` (`accepted | needs_review | blocked`). If `verifyBeforeApply` is true and there are no blocking errors, the workflow path is extended with a `proof_verification` step and the final state becomes `needs_review` rather than `accepted` — directly encoding the platform-wide "verification gate" pattern into the shared form engine itself, rather than leaving each domain to reimplement it.
- **`isEmpty()`** — a small internal utility treating `null`/`undefined`/blank strings/empty arrays as "empty," used consistently for required-field checks.

Because this package has zero backend or transport dependencies, it can run identically inside the Next.js admin-web SOP builder/preview UI, the Android app (via a JS bridge or shared logic port), and the `operator-mobile` app, guaranteeing that "is this SOP submission valid?" is answered the same way everywhere, rather than being reimplemented (and potentially diverging) per client.

### 2.3 `@goatos/mobile-forms-runner` — SOP Form Rendering Layer

`mobile-forms-runner` sits directly on top of `forms-dsl` and is the bridge between the abstract SOP DSL and a renderable UI form. Its single exported function, `buildRunnerModel(dsl, proofPolicy, answers, proofRefs)`:

1. Delegates validation logic entirely to `evaluateForm()` from `forms-dsl` (no duplicated business rules).
2. Maps each `SOPField` to a concrete UI component name via `componentFor()` — a pure switch statement translating the ten DSL field types into ten component identifiers (`TextInput`, `NumberInput`, `DateTimeInput`, `Select`, `MultiSelect`, `GoatLookup`, `AnimalIDScan`, `LocationPicker`, `PhotoProof`, `VideoProof`).
3. Produces a `RunnerModel` — `title`, an array of `RunnerFieldModel` (`key`, `label`, `component`, `required`, `blocked`, optional `message`), plus `canSubmit`, `finalState`, `workflowPath`, and `errors` lifted straight from the `EvaluationResult`.

This package is the "renderer contract": a mobile client can consume a `RunnerModel` and know exactly which widget to draw and whether the submit button should be enabled, without embedding any SOP-specific conditional logic itself.

### 2.4 `@goatos/device-client` — Device Registration Gate

A minimal, dependency-free package encoding the decision logic for whether an Android device is allowed to execute field tasks. Its core type, `DeviceGate`, is a discriminated union of exactly three states:

- `{ kind: "ready", device_id? }` — the device may proceed.
- `{ kind: "registration_required", reason }` — the device must complete registration first.
- `{ kind: "revoked", reason }` — the device's access has been withdrawn.

`evaluateDeviceGate(deviceState)` is a pure function: if device gating is not `required` for the tenant/config, or if `status === "active"`, it returns a `ready` gate (via the internal `readyGate()` helper, which correctly omits `device_id` when unknown rather than defaulting to an empty string); a `"revoked"` status maps to the `revoked` gate with a fallback reason string; anything else defaults to `registration_required`. Because this logic is entirely side-effect-free and takes only plain data in/out, it is trivially unit-testable and portable to any TypeScript-capable client runtime.

### 2.5 `@goatos/media-client` — Local Proof Upload State Machine

`media-client` models the client-side lifecycle of a locally captured proof artifact (`LocalProofDraft`) as it moves through upload states: `pending → uploading → completed | failed`. Three pure transition functions are exported:

- `markUploadStarted(draft)` — clears any prior `error` field and sets state to `uploading`.
- `markUploadCompleted(draft, proofId)` — clears `error`, sets state to `completed`, and attaches the server-assigned `proof_id`.
- `markUploadFailed(draft, error)` — sets state to `failed` and records the `error` message (while preserving other draft fields).

Each function returns a **new** object rather than mutating its input, making these safe to use directly as reducers in state-management systems (e.g., a mobile app's local outbox queue) without additional immutability wrappers. The `upload_state` vocabulary (`pending|uploading|completed|failed`) is intentionally identical to the one used in `forms-dsl`'s `ProofReference` and the `sop-submission`/`sop-preview-dry-run` JSON Schemas, so the same four-state lifecycle is shared end-to-end from local capture through DSL evaluation to backend schema validation.

## 3. Contracts & Schemas (`./contracts`)

The `contracts/` directory is the **single source of truth** for cross-service data shapes. It is organized into three sub-trees:

```
contracts/
├── openapi/        → REST API contracts (app-api, admin-api, analytics-api, ceo-ai-ask-stream)
├── jsonschema/      → standalone JSON Schema definitions for events, decisions, SOP forms
└── examples/        → concrete payloads validated against the above, by CI
```

### 3.1 OpenAPI Specifications

Three REST surfaces are defined as OpenAPI 3.1 documents:

- **`app-api.yaml`** — the largest and most active contract, covering mobile/field-app-facing routes (goat search/passport, herd-signals ingestion and live status, vaccination execution/operations/schedule, `/app/tasks`, etc.). It is the direct source for `api-client`'s generated `app-api.ts` (~27.5k generated lines), reflecting the breadth of endpoints field apps consume.
- **`admin-api.yaml`** — the admin-web-facing surface (~330 KB / ~12,000 lines), covering auth session audit events, admin goat management, locations, operator/workforce management, the SOP Builder, tasks, procurement source entry, operations audit, and HR roster. Its `info.description` explicitly notes that deprecated verticals (import-review, identity-review, legacy sync, counts, mortality dashboards) are **not active contracts** — a documented signal that the spec is deliberately pruned to only currently-supported routes, preventing stale endpoints from being perpetuated through code generation.
- **`analytics-api.yaml`** — currently a deliberately **empty/reserved** contract (`paths: {}`, `schemas: {}`), with an explicit description warning maintainers not to "revive old counts, mortality, or identity-count dashboard endpoints" unless the product scope reopens that vertical with proper projection-backed APIs. This is a notable governance pattern: an intentionally inert contract file acts as a placeholder and a guardrail against ad hoc analytics endpoint sprawl.
- **`ceo-ai-ask-stream.yaml`** — a standalone, additive OpenAPI fragment (not yet merged into the base admin spec) describing the Server-Sent-Events (SSE) streaming transport for the `POST /api/ceo-ai/ask` leadership-assistant endpoint. It documents a `type`-discriminated SSE frame protocol (`token` frames followed by exactly one terminal `final` or `error` frame, with `: keepalive` heartbeat comments clients must ignore), a `stream=1` query-parameter negotiation switch, `Cache-Control: no-store` / `X-Accel-Buffering: no` response headers to defeat proxy buffering, and an explicit "Internal Tracking rule": the stream may carry only synthesized answer tokens, **never** step traces, chain-of-thought, tool timelines, or raw SQL. Its schema names are deliberately namespaced (`CeoAiStream*`) so the fragment can later be folded into the primary admin-api spec without collision.

### 3.2 JSON Schemas

Standalone JSON Schema (2020-12 draft) documents govern payload shapes that are not simple REST request/response bodies — primarily domain events, audited decisions, and the SOP form/execution pipeline:

- **`domain-event-envelope.schema.json`** — the canonical envelope for every outbox/domain event in the platform. It enforces `additionalProperties: false` and requires 17 fields including `event_id`, `event_type` (a closed enum of well over 100 concrete event names spanning identity, health, vaccination, calendar, counts, verification, weighing, feed, PC-care, procurement, workforce, leadership tasks, and pen visits), `schema_version` (semver-pattern string), `schema_ref`, `aggregate_type`/`aggregate_id`, `occurred_at`/`recorded_at` timestamps, `producer` (service/module/version), `idempotency_key`, `actor`, `subject_type`/`subject_id`, a `visibility_scope` (tenant/custodian/farm/park/shed/cohort), `evidence_refs`, `payload`, and `trace_id`. An optional `replay` block (`is_replay`, `replay_of_event_id`, `dlq_repair_id`, `attempt`) supports the outbox DLQ-repair/replay pipeline described in the platform's event-bus architecture. Because the event-type enum is exhaustive and centrally defined here, adding a new domain event type is a deliberate, reviewable change to this single schema file rather than an implicit convention scattered across 45+ backend modules.
- **`decision-record.schema.json`** — models audited identity-resolution decisions (e.g., `merge_goats`, `attach_identifier`, `reject_match`). Its description states the governing policy explicitly: *"AI may propose but cannot approve canonical truth."* This is enforced structurally: `decided_by_type` is one of `human | system_rule | import_policy | ai_proposal`, and `decision_state` is one of `proposed | approved | rejected | needs_review` — an AI-proposed decision can populate `decision_state: "proposed"` but the schema/consuming logic elsewhere gates any `"approved"` transition behind human or system-rule attribution. The schema also enforces `evidence.evidence_refs` to have `minItems: 1`, meaning no decision record can exist without at least one supporting evidence reference, and tracks `affected_goats`, `identifier_actions`, optional AI provenance (`model_version`, `confidence` bounded `0..1`), and a `reviewer_id`.
- **`sop-form-version.schema.json`** — the JSON Schema counterpart to the `forms-dsl` TypeScript types (`schema_version` pinned via `const: "goatos.sop-form.v1"`, the same ten-value field-type enum, the same five rule types and four comparison operators, and the same `workflow` node/edge shape with node types extended to include `accepted|rework|rejected|blocked` terminal states). Unlike the tightly-closed event/decision schemas, this one sets `additionalProperties: true` at the top level and on nested objects, allowing forward-compatible extension of SOP definitions without breaking older consumers.
- **`sop-proof-policy.schema.json`** — governs how much proof a given SOP requires: `required` (boolean), `subject_scope` (`batch|goat|shed|task`), allowed `types` (`photo|video`), `minimum_count`/`minimum_count_per_subject`/`maximum_count_per_subject`, `capture_source` (currently only `in_app_camera`, closing off gallery-picked media as a valid proof source), `verify_before_apply`, and a `retention_policy` enum (`operational_90d|standard_1y|critical_7y|legal_hold`) that ties directly into media/data-retention governance. Notably it declares `"not": { "required": ["scope"] }` — an explicit negative constraint rejecting a legacy/incorrect `scope` field name, guarding against a specific historical naming mistake.
- **`sop-submission.schema.json`** and **`sop-preview-dry-run.schema.json`** — twin schemas for, respectively, a final SOP submission (`sop_version_id`, `idempotency_key`, `answers`, `proof_refs`, strict `additionalProperties: false`) and a dry-run preview of the same (`answers`, `proof_refs`, optional free-form `context`, also `additionalProperties: false` at the top level). Both share an identical `proof_ref` definition (`proof_id`, `proof_type`, `subject_type`, `subject_id`, `upload_state`, `metadata`) matching the `ProofReference`/`LocalProofDraft` shapes in the TypeScript packages — one more instance of the domain's consistent "same vocabulary everywhere" discipline.
- **`protocol-rule-dsl.schema.json`** — a schema for the rule language driving protocol/obligation generation (vaccination-style schedules, feed rations). It models `eligibility` filters (animal stage, sex, breed, age bands, reproductive-state exclusions), `missed_dose_policy`, `stock_policy` (vaccine lot picking, cold-chain requirements), a `schedule` array (per-dose sequencing, due windows, revaccination intervals, proof policy references), `session_timing` for multi-session drives, and `inventory_policy` (reserve/consume/release modes). This schema is fully closed (`additionalProperties: false` throughout), reflecting that protocol rules are governed, versioned configuration rather than free-form data.

### 3.3 Example Payloads and the Validation Harness

The `contracts/examples/{app,decisions,events,shared,forms,submissions}` directories hold hand-authored, fully-synthetic (no real farm/animal data) example payloads: a goat search response, a goat passport response, an error envelope, a `goat.identifier.added` domain event, and an `merge_goats` decision record. Every example is deliberately labeled as `synthetic_*` in its `source_system`/description fields, underscoring that these fixtures exist purely for contract validation, not as real production data.

These examples are not merely documentation — they are actively checked by `tools/contract-validation/validate-contracts.mjs`, a Node/ESM script (using `@apidevtools/swagger-parser`, `ajv`/`ajv-formats` with the JSON Schema 2020-12 dialect, and the `yaml` parser) that runs as part of CI. Its responsibilities, in order:

1. **`validateRequiredFiles()`** — asserts the five foundational contract files exist (both event/decision JSON Schemas and all three OpenAPI specs).
2. **`validateJsonSchemas()`** — recursively finds every `*.schema.json` file under `contracts/jsonschema` and compiles it with Ajv, catching schema-authoring errors (invalid JSON Schema syntax) before they can propagate.
3. **`validateOpenApiSpecs()`** — runs `SwaggerParser.validate()` against every OpenAPI file, catching structural/spec violations.
4. **`validateVaccinationCursorContract()`** — a bespoke, hard-coded assertion that `/vaccination/execution`, `/vaccination/operations`, and `/vaccination/schedule` GET endpoints exist, accept a `cursor` query parameter, and their `200` response schema exposes a `nextCursor`/`next_cursor` field — codifying a pagination convention as an enforced contract rule rather than a code-review convention.
5. **`validateAppTaskMobilePaginationContract()`** — an equally specific assertion for `/app/tasks`: the `limit` query parameter must default to and cap at exactly `20` (protecting mobile clients on constrained connections from accidentally requesting large pages), a `cursor` parameter must exist, and the `TaskListResponse` schema must require `items` (capped at `maxItems: 20`), a non-negative `total`, boolean `has_more`, and a nullable-string `next_cursor`.
6. **`validateExamples()`** — cross-checks every file under `contracts/examples/**/*.json` against a registered `exampleChecks` list, each entry indicating whether the example should validate against a standalone JSON Schema (`kind: "jsonschema"`) or a schema dereferenced out of an OpenAPI spec's `components.schemas` (`kind: "openapi"`). Critically, any example file *not* present in the explicit `exampleChecks` list causes an immediate failure ("Contract examples need explicit schema checks") — meaning new example fixtures cannot be silently added without being wired into validation, closing off a common way for contract test coverage to quietly degrade over time.

The script's `main()` runs all of the above and prints a summary count of specs/schemas/examples validated, exiting non-zero on any failure — making it directly wireable into CI as a required merge gate.

## 4. Developer & Operational Tooling (`./tools`)

`tools/` is a large, purpose-organized collection of ~20 sub-directories covering CI orchestration, contract validation, database schema management, AI-agent documentation sync, and data repair. Representative highlights:

### 4.1 `postgres-ci.sh` — Shared Postgres CI Primitives

A Bash library (not a standalone script — it is `source`d by other tools) providing reusable functions for any CI job that spins up an ephemeral Dockerized PostgreSQL instance:

- `postgres_ci_log_container(name)` — dumps container logs to stderr for post-mortem debugging.
- `postgres_ci_is_transient_connection_error()` — a `grep -Eiq` filter matching known-transient Postgres startup/shutdown/recovery error strings (e.g., *"the database system is starting up"*, *"connection refused"*, *"server closed the connection unexpectedly"*). This lets calling scripts distinguish "Postgres just isn't ready yet, retry" from a genuine SQL/schema error that should fail fast.
- `postgres_ci_wait_ready(container, user, db, attempts=90)` — polls up to 90 times (roughly 90 seconds), first checking the container is still running (failing fast with logs if it exited early), then confirming both `pg_isready` and an actual `SELECT 1` succeed before declaring readiness.
- `postgres_ci_psql(...)` and `postgres_ci_pg_dump(...)` — wrap `docker exec ... psql`/`pg_dump` with a 5-attempt retry loop that only retries on transient errors (as detected above), backing off `sleep "$attempt"` seconds between tries, and dumping container logs plus the failing output on a genuine (non-transient) failure.

This library is consumed directly by `tools/sqlc/dump-schema.sh`, which boots a real Postgres container, applies every `goose`-formatted migration under `backend/migrations/postgres` (parsing out only the `-- +goose Up` section via `awk`), and `pg_dump`s the resulting schema-only DDL into six sqlc-consumed `schema.sql` files (`identity`, `protocol`, `obligation`, `inventory`, `vaccination`, `feed`) — ensuring the sqlc code generator always compiles against a schema that was actually produced by running the real migration chain, not a hand-maintained snapshot that can drift from what migrations actually produce.

### 4.2 `sqlc` Toolchain Version Pinning

`tools/sqlc/check-version.sh` reads a pinned version string from `tools/sqlc/sqlc.version` and compares it against the locally installed `sqlc version` output (or a `$SQLC` binary override), failing loudly if they differ. This guarantees every engineer and every CI runner generates Go/Postgres data-access code with an identical `sqlc` release, preventing subtle generated-code differences from becoming spurious diffs or bugs.

### 4.3 CI Guardrail Ecosystem (`tools/ci`)

The `tools/ci` directory hosts the backbone of GoatOS's local-and-remote CI parity strategy:

- **`run-local-ci.sh`** (~990 lines) — the authoritative entry point mirroring `.github/workflows/ci.yml` job-for-job (`common`, `backend`, `query-plans`, `admin-web`, `android`). Its header comments articulate an explicit policy: a GitHub Actions platform/billing failure is never a legitimate reason to block a merge — a green `make ci-local` run against the exact pushed SHA is the authoritative gate. It supports scoped invocation (`auto`, `all`, or a single job name) and environment-variable opt-ins for expensive suites (e.g., `GOATOS_RUN_POSTGRES_TESTS=1`).
- **`ci-scope.mjs`** and **`component-paths.json`** — implement path-based CI scoping: `component-paths.json` maps file-path prefixes to logical components (`backend`, `adminWeb`, `android`) and defines cross-cutting `fanout` groups (e.g., a change under `contracts/` or `packages/api-client/` is explicitly configured to fan out to `backend`, `adminWeb`, *and* `android` jobs simultaneously — a direct, codified acknowledgment that this Shared Contracts domain is a true cross-component dependency whose changes must be validated against every consumer, not just one). A `forceFull` list (workflow files, `Makefile`, `go.work`, root `package.json`) always triggers every job regardless of scoping, and a `commonOnly` list restricts documentation-only changes to the lightweight common job.
- **`check-large-files.mjs`** — a portable (single Node process, avoiding macOS's ancient Bash 3.2) guard that walks every Git-tracked file via `git ls-files -z`, flags any file exceeding `GOATOS_MAX_TRACKED_FILE_BYTES` (default 5 MiB), and exempts lockfiles (`package-lock.json`, `pnpm-lock.yaml`) from the limit — protecting repository size/clone performance from accidental large binary commits.
- **`check-git-identity.mjs`**, **`check-review-lens-ledger.mjs`**, **`check-guardrail-registration.mjs`**, **`check-stg-promotion.mjs`**, **`analyze-rebase-scope-widening.mjs`**, **`land-main.sh`**, **`check-push-hook-freshness.sh`**, and various Android-specific scripts (`android-ui-diff.sh`, `gradle-worktree-lock.sh`, `check-android-screenshot-proof.sh`) round out an unusually mature suite of merge-time guardrails — including a `guardrail-manifest.json` (86 KB) that appears to be a central registry of enforced CI checks, and `ratchet-guard.*.json` files that likely implement "ratcheting" quality baselines (never allowing a metric like exception count or telemetry volume to regress) tracked alongside `tools/exception-guard` and `tools/telemetry-guard`.

### 4.4 Quality Ratchets: `exception-guard`, `telemetry-guard`, `scale-guard`

Three related tools enforce non-regression on operational quality metrics rather than functional correctness:

- **`tools/exception-guard/exception_guard.py`** (~40 KB, the largest single script in `tools/`) together with a `baseline.json`/`baseline-v2.json` pair and `config.json` — almost certainly scans the codebase or logs for exception-handling patterns and compares counts/categories against a recorded baseline, failing if the situation worsens ("ratcheting" the baseline forward only when it improves).
- **`tools/telemetry-guard/telemetry_guard.py`** (~22 KB) with its own `baseline.json`/`baseline-v2.json`/`config.json` — analogous ratcheting for telemetry/observability instrumentation coverage or volume.
- **`tools/scale-guard/scaleguard.go`** (~30 KB, a standalone Go module with its own `go.mod`) — a Go-implemented guard, likely checking backend code for scale-unsafe patterns (e.g., unbounded queries, missing pagination, N+1 patterns) given its co-location with `component-paths.json`'s `queryPlans` fanout group covering `backend/internal/*/adapters/postgres/` and `backend/migrations/`.

### 4.5 Data Repair (`tools/data-repair`)

Two hand-authored, environment-specific SQL scripts — `stg-mandela1-class-c-repair.sql` (~15.9 KB) and `stg-partition-catalog-repair.sql` (~11.8 KB) — represent targeted, one-off data-correction operations against the staging environment. Their naming convention (`stg-<incident-or-farm>-<issue>-repair.sql`) suggests this directory serves as an audit trail of past production/staging data-integrity incidents and their remediations, rather than a reusable tool library — valuable historical context for anyone debugging a recurrence of similar data issues.

### 4.6 AI Coding-Agent Documentation Sync (`tools/agent-docs`)

This sub-domain solves a distinct problem: keeping AI coding assistants (Codex, Claude Code) grounded in **version-accurate** framework documentation for the specific library versions GoatOS actually uses, rather than relying on a general-purpose LLM's (potentially stale or version-mismatched) training data.

- **`context7-docs.config.tsv`** — a tab-separated configuration table of ~29 rows, each specifying a `slug`, a Context7 `libraryId` (often pinned to an exact version, e.g., `/vercel/next.js/v16.2.9`, `/react/react/v19.2.7`), and a natural-language `query` describing the topic to fetch (e.g., *"app router route handlers caching server actions revalidatePath"*). Coverage spans the full technology stack in use: Next.js 14 and 16 (both tracked, likely for a live migration), React 18/19 (including a dedicated *performance* query variant), TanStack Query v5, Firebase JS/Android SDKs, Playwright, Recharts, Jetpack Compose (including a performance-focused variant), Hilt, OkHttp, CameraX, Media3, WorkManager, Kotlin, Gradle, OpenTelemetry-Go, pgx, PostgreSQL, BigQuery/Pub/Sub/Cloud Tasks Go clients, the OpenAPI specification itself, and Ajv.
- **`bootstrap-context7-secret.sh`** — fetches the `context7-api-key` and `graphify-gemini-api-key` secrets from Google Secret Manager (hard-restricted to the `goatos-stg` project unless `GOATOS_ALLOW_NON_STG_AGENT_DOCS_PROJECT=1` is explicitly set) into a gitignored, `chmod 600` local env file (`~/.config/goatos/context7.env`). It requires the active `gcloud` identity to be a `*@mesha.sg` account, and offers `--configure-codex`/`--configure-claude` flags to additionally register the Context7 MCP (Model Context Protocol) server with the respective AI coding tool.
- **`ensure-context7.sh`** — an idempotent pre-flight check: if `CI`/`GITHUB_ACTIONS` is detected, it exits immediately (agent-doc sync is a local-developer convenience, never a CI dependency); otherwise it live-checks both the Context7 and Gemini APIs (a real authenticated `curl` call to each), and only if either check fails and a Mesha `gcloud` account is active does it invoke `bootstrap-context7-secret.sh` to refresh credentials. A `--doctor` mode exists for diagnostic use that tolerates an unauthenticated local clone gracefully rather than failing.
- **`sync-context7-docs.sh`** — the main sync driver: reads `context7-docs.config.tsv` line by line, calls the Context7 v2 context API (`https://context7.com/api/v2/context`) per row with the configured `libraryId`/`query`, writes successful responses (HTTP 200 and >200 bytes) as Markdown files into a primary cache directory (`.agent-docs/context7/current/`, gitignored) and mirrors them into a non-hidden `agent-docs/context7/current/` directory for downstream "Graphify" scanning. It then optionally builds a knowledge graph over the fetched docs by invoking the `graphify` CLI (via `uvx`, defaulting to the `gemini` backend model `gemini-3.1-pro-preview`, with `claude`/`openai` backend alternatives gated on their respective API keys being present) — but treats any Graphify failure as non-fatal, since the raw Markdown doc cache remains useful even if graph-building fails.

Collectively, this sub-domain demonstrates a deliberate investment in **AI-agent developer experience**: rather than trusting an LLM coding assistant's implicit knowledge of, say, "Next.js app router caching," the toolchain pulls precise, version-pinned documentation for the actual dependency versions pinned in the repo, on demand, with safe multi-account/CI-skip guards.

```mermaid
flowchart TD
    A[OpenAPI YAML Contracts\n(app-api, admin-api, analytics-api)] --> B[openapi-typescript CLI\n'generate' script]
    B --> C[Generated TS Types\n(generated/app-api.ts, admin-api.ts, analytics-api.ts)]

    G --> H[Contract Validation Tooling\n(./tools/contract-validation)]
    F --> H

    I[forms-dsl package\nSOPFormDSL, SOPField, SOPRule types] --> J[mobile-forms-runner\nevaluateForm + componentFor]
    J --> K[RunnerModel / RunnerFieldModel\nrendered in mobile app]

    L[device-client\nDeviceRegistrationInput/DeviceGate] --> M[evaluateDeviceGate / readyGate]
    M --> E

    N[media-client\nLocalProofDraft] --> O[Upload state transitions\npending->uploading->completed/failed]
    O --> E

    P[CI Pipeline] --> Q[postgres-ci.sh\ncontainer logs + transient error detection]
    P --> R[agent-docs scripts\nbootstrap/ensure/sync Context7 docs]
    R --> S[Context7/Gemini API\n+ gcloud secrets]
    H --> P
```

Concretely:

- **Admin-web** and **operator-mobile** import `@goatos/api-client` for all typed HTTP access to the Go backend, and `@goatos/forms-dsl` / `@goatos/mobile-forms-runner` for SOP form rendering and validation.
- **goatos-android** relies on the same `device-client` and `media-client` state-machine contracts (or their Kotlin equivalents mirroring the same vocabulary) to gate device readiness and track proof uploads consistently with the web/mobile TypeScript stack.
- The **backend** is the ultimate producer of the OpenAPI contracts and the JSON Schema-governed event/decision payloads; it does not consume `packages/*` directly, but its API surface and event vocabulary are exactly what `contracts/openapi/*.yaml` and `contracts/jsonschema/*.schema.json` describe — any backend route or event-type addition must be reflected here before client-side type generation can pick it up.
- **CI** (`tools/ci/run-local-ci.sh`, GitHub Actions) invokes `tools/contract-validation/validate-contracts.mjs` and the `api-client` `check` script as required gates, and uses `component-paths.json`'s explicit `fanout` rule to force `backend` + `adminWeb` + `android` jobs whenever `contracts/` or `packages/api-client/` changes — directly operationalizing the fact that this domain is a shared dependency of every other component.

## 6. Design Principles Observed

1. **Single source of truth, code-generated downstream.** OpenAPI/JSON Schema files are authored once; TypeScript types are mechanically derived, and any manual edit to a generated file is caught by regenerate-and-diff (`api-client`'s `check` script).
2. **Closed vocabularies wherever correctness matters, open vocabularies wherever extensibility matters.** Audit-critical schemas (`domain-event-envelope`, `decision-record`, `sop-submission`) use `additionalProperties: false` and enumerated types; the SOP form-definition schema deliberately allows `additionalProperties: true` for forward compatibility.
3. **Shared state-machine vocabulary across languages/layers.** The `pending|uploading|completed|failed` upload-state and `photo|video|attachment` proof-type enums recur identically across `forms-dsl`, `media-client`, and two JSON Schemas — a single vocabulary enforced structurally rather than by convention.
4. **Pure functions over side-effecting abstractions.** `device-client`, `media-client`, and `forms-dsl`'s `evaluateForm` are all side-effect-free, taking and returning plain data — maximizing testability and portability across the web/mobile boundary.
5. **CI as an enforced contract**, not documentation. Pagination conventions (`cursor`, capped `limit`), example-payload coverage, generated-file freshness, and even AI-agent doc availability are all checked mechanically rather than left to code-review discipline.
6. **Governance embedded in schema comments and structure.** The AI-cannot-approve-canonical-truth rule in `decision-record.schema.json`, the "no chain-of-thought in the SSE stream" rule in `ceo-ai-ask-stream.yaml`, and the "do not revive deprecated analytics endpoints" warning in `analytics-api.yaml` all encode organizational policy directly into contract artifacts that generate compile errors or CI failures if violated — a notably rigorous approach to keeping architecture decisions enforceable rather than merely documented.
