# Boundaries & Interfaces

This document catalogs how the outside world talks to Goat OS: the HTTP APIs the clients and integrations call, the command-line entry points that run the services and jobs, the domain-event contracts that connect modules, the IoT ingestion bridges, and the environment configuration that wires it all together. The guiding rule across every boundary is the one stated throughout the codebase — the backend owns the contract, clients render it — so these interfaces are not incidental plumbing; they *are* the product's surface.

---

## 1. HTTP APIs (OpenAPI)

Goat OS exposes four OpenAPI contracts, each for a distinct audience. Keeping them separate matters because it lets the mobile surface evolve independently of the admin surface, and it keeps the read-only analytics stream out of the operational APIs.

| Contract | File | Paths | Audience |
|----------|------|-------|----------|
| App API | `contracts/openapi/app-api.yaml` | 290 | The Android field app and mobile-facing surfaces |
| Admin API | `contracts/openapi/admin-api.yaml` | 97 | The admin-web console |
| CEO AI stream | `contracts/openapi/ceo-ai-ask-stream.yaml` | 1 | The leadership assistant's streaming answer endpoint |
| Analytics API | `contracts/openapi/analytics-api.yaml` | — | Analytics egress contract |

### 1.1 App API shape

The App API is by far the largest surface, and its path prefixes read like a table of contents for the farm's daily work. The grouping below (from the actual path counts) shows where the operational weight sits — the `/app/*` namespace alone carries 118 of the 290 paths, because it is the operator's whole world: bootstrap, tasks, PC care, weighing, pen visits, devices.

| Prefix | Paths | What it serves |
|--------|-------|----------------|
| `/app/*` | 118 | Bootstrap, tasks, PC care, weighing, devices, pen visits — the operator surface |
| `/vaccination/*` | 25 | Drives, execution, anchors, verification queue |
| `/sales/*`, `/procurement/*` | 30 | Vendor register, loads, leads, feed purchases |
| `/feed-config/*`, `/feed-direction/*`, `/feed-analytics/*` | 29 | Ration authoring, direction sheets, analytics |
| `/verification/*` | 11 | Verifier queue, verdicts, sampling |
| `/herd-signals/*` | 11 | IoT packets, live signals, gateways, tag mappings |
| `/weighing/*` | 10 | Campaigns, growth, shed weights, demographics |
| `/protocols/*`, `/health-config/*` | 16 | Vaccination and health protocol authoring |
| `/calendar/*`, `/action-center/*`, `/control-tower/*`, `/workflows/*` | 11 | Command-lens reads |
| `/counts/*`, `/health/*`, `/toxin/*` | 7 | Herd register, clinical cases, aflatoxin tests |

### 1.2 Representative endpoints

A few endpoints anchor the whole design. `GET /app/bootstrap` returns the mobile nav contract, actor identity, device state, and feature flags — it is the first call every session makes. `GET /admin-web/bootstrap` is its web twin, returning per-route page contracts. `POST /verification/items/{item_id}/verdict` is the verifier-only verdict route. `GET /goats/{goat_id}/passport` returns a goat's full read-only vaccination story. And the weighing capture routes (`POST /app/weighing/campaigns/{id}/animal-observations`, `.../submit`, `.../close`) show the scan-and-submit shape with its unconditional close gate.

### 1.3 Authentication and integration guidance

Every protected route expects a Firebase-issued JWT as a Bearer token, verified against a JWKS endpoint in production (`GOATOS_AUTH_MODE=jwks`). Permissions are resolved server-side from the caller's grants — never from anything in the request body — so a client cannot escalate by naming a scope. The recommended integration pattern is: authenticate with Firebase, call bootstrap to learn what the actor may see, then call the specific read/write endpoints the contract advertised. Writes should carry an `Idempotency-Key` header so a retried request returns the original result rather than double-applying.

## 2. Command-line entry points

The backend ships as a set of Go binaries under `backend/cmd/`. The two that run continuously are the API service and the kernel worker; the rest are focused jobs, importers, and seed tools. Understanding this split is understanding the runtime: synchronous request handling lives in one binary, all time-driven work in another, and everything else is an operational tool you run deliberately.

| Binary | Path | Role |
|--------|------|------|
| API service | `backend/cmd/api` | The 290+ endpoint HTTP server; entry `main.go` calls `bootstrap.NewAPI` |
| Kernel worker | `backend/cmd/kernel-worker` | The consolidated worker: obligation sweep, outbox relay, reminders, closeouts, generation, housekeeping |
| Device gateway | `backend/cmd/device-gateway` | Fronts IoT device ingestion |
| Migrate | `backend/cmd/migrate` | Applies Postgres migrations (checksum-verified) |
| Domain-event consumer | `backend/cmd/domain-event-consumer` | Pub/Sub subscriber running appliers + workflow consumers |
| Outbox relay / DLQ | `backend/cmd/outbox-relay`, `outbox-dlq` | Standalone relay + dead-letter handling |
| Herd-signals bridges | `backend/cmd/herd-signals-mqtt-bridge`, `herd-signals-udp-bridge` | Decode BLE packets from MQTT/UDP |
| Notification dispatcher | `backend/cmd/notification-dispatcher` | Claims and sends queued FCM pushes |
| Seed tools | `backend/cmd/seed-*` | Roster, vaccination, weighing, STG login-grant seeds |
| Import tools | `backend/cmd/import-*` | Feed purchases, procurement vendors, sales DB imports |
| MCP server | `backend/cmd/mcp` | Model-Context-Protocol entry for the leadership assistant |

Most of the `seed-*` and `import-*` tools are one-shot operational commands; the guarded local deploy launcher and the STG Slack-triggered Cloud Build path (not GitHub Actions) are the sanctioned ways to ship, per the deployment contract.

## 3. Domain-event contracts

The most important *internal* interface is the domain-event spine. Modules do not call each other directly for coordination; a producer writes a canonical row and an outbox message in one transaction, and consumers react. The full registry lives in `context/architecture/domain-event-registry.json`, and the rule enforced by `make domain-event-architecture-guard` is that both ends of every event must exist — a producer with no consumer is a silent drop, a consumer with no producer is dead code.

| Event (example) | Producer | Consumer(s) |
|-----------------|----------|-------------|
| `goat.created` / `goat.exited` | identity | obligation (generate / cancel) |
| `goat.location.changed` / `goat.stage_changed` | counts/identity | vaccination (rescope + re-evaluate) |
| `protocol.published` | protocol | obligation (backfill generation) |
| `vaccination.completed` | vaccination | obligation (repeat generation) |
| `verification.verdict.approved` / `.rework` | verification | every producer's applier (via eventwiring) |
| `weighing.shed_submission.completed` | weighing | counts (pen reconciliation) |
| `counts.death.reported` | counts | health (case state) |
| `goat.sale_allocated` | sales | notification (feed director notice) |

The single registration point (`backend/internal/eventwiring/appliers.go`) wires these consumers once for all three buses (in-process, outbox relay, Pub/Sub), so a handler can never be live on one path and missing on another.

## 4. IoT ingestion boundary

Physical BLE tags reach the system through gateways that forward packets over MQTT or UDP. Both transports feed the same decoder (`backend/internal/herdsignals/gateway/decode.go`, recognizing the HoneyComm UUID 0xAB4C), so a new transport is a new bridge command reusing one decode path. Packets are stamped with a server-side `received_at` at ingestion and deduplicated on (tenant, tag, received_at) — the device's own clock is a diagnostic hint, never trusted for correctness.

## 5. Configuration (environment variables)

The backend is configured entirely through environment variables, resolved in `bootstrap.ConfigFromEnv` (`backend/internal/bootstrap/api.go:226`). The table below covers the ones that most change behavior; the intent column explains *why* each exists rather than merely what it holds.

| Variable | Purpose / intent |
|----------|------------------|
| `GOATOS_ENV` | Environment name; gates dev-only affordances (local media, dev headers) so production fails closed on shortcuts |
| `GOATOS_HTTP_ADDR` | The bind address for the API service — the one knob phone-QA remaps rather than repointing the shared stack |
| `GOATOS_AUTH_MODE` | `jwks` selects the production RS256/ES256 verification path; other modes are for local/dev |
| `GOATOS_AUTH_ISSUER` / `_AUDIENCE` / `_JWKS_URL` | The Firebase token contract the backend verifies against — the trust anchor for every request |
| `GOATOS_AUTH_ALLOWED_EMAILS` | Optional allowlist gate for who may obtain a session at all |
| `GOATOS_FIREBASE_PROJECT_ID` | Firebase project for identity plumbing (may remain `goatos-stg` while public names are production) |
| `GOATOS_GCS_BUCKET` / `_SERVICE_ACCOUNT_JSON` | Proof-media storage target and credentials — where clips live and how they are signed |
| `GOATOS_MEDIA_STORAGE` / `GOATOS_LOCAL_MEDIA_DIR` | Selects GCS vs. local media; local is allowed only in non-production envs |
| `GOATOS_APPCHECK_*` | Optional Firebase App Check enforcement on the mobile surface |
| `GOATOS_LOG_LEVEL` / `GOATOS_OBS_SINK` | Observability level and sink (`stdout_json` / `otlp` / `gcm`) |
| `GOATOS_SWEEPER_DUE_BEFORE` | Override for the obligation sweep's due-before cutoff (defaults to end of the IST business day) |
| `DATABASE_URL` | The Postgres DSN — deliberately never inferred; the local stack and phone-QA rules pin exactly which database each process uses |

The strongest configuration discipline in the project is around the database DSN: which Postgres a process talks to is never guessed from a stale shell variable, and phone-QA runs on a non-default port with a remapped tunnel precisely so a test can never write into the staging replica.

## 6. Integration recommendations

To integrate with Goat OS, treat the OpenAPI contracts as the source of truth and generate a typed client from them rather than hand-rolling requests — this is exactly what the Android app does (its only backend coupling is `app-api.yaml`). Authenticate through Firebase, call bootstrap first to discover the authorized surface, and send idempotency keys on writes. For internal extension, add a domain event with both a producer and a registered consumer (never one without the other), and register any new verifiable workflow as a verification category so it flows through the one shared queue. Do not read a `ceo_ai.*` reporting view from an operational path, and do not invent a private scheduler — reuse the kernel chain.
