## ADG-specific slowness check added 2026-09-23

The ADG investigation used the PR branch code against the real STG Cloud SQL database through the local proxy, not a fake seed and not the live STG website. The live STG website is still old code until this PR is merged and deployed, so these numbers prove the repository/API path on STG data, not post-deploy browser latency.

Same tenant and active parks as STG, default male ADG scope, window 2026-08-03 through 2026-09-23:

| ADG read | Before this ADG patch | After this ADG patch |
| --- | ---: | ---: |
| growth assumptions | 200.8ms | unchanged, now overlaps landing dates |
| 400-day landing weighing dates | 324.2ms | unchanged, now overlaps assumptions |
| shed_weights | 1.066s with procurement load buckets | 793.0ms with include_loads=false |
| growth_general | 438.8ms | unchanged |
| demographics_composition | 392.8ms | unchanged |

The direct shed_weights reduction is about 273ms on the measured STG run. The frontend also no longer waits for growth assumptions before starting the landing date lookup, so the cold path removes about the smaller of those two waits (about 200ms in this run). Total avoidable wait removed from the ADG General cold path is therefore about 470ms on this STG-data probe.

Why earlier fixes did not cover this: the prior work in PR376 fixed notification-feed CTE pagination, notification-bell route fanout, and Cloud Run max-instance persistence. Those reduce general API saturation and a specific notification query. ADG General had separate costs: it serialized assumptions before the landing-date lookup, and the shed_weights read always computed procurement load buckets even on tabs that render only shed rows and summary cards. This patch fixes those ADG-specific costs. It does not remove the sex/origin scope and identity-map work still required by the shed rows, and it does not prove live browser improvement until deployed.
