## Machine Guard

Guard: make operational-location-guard (runs in make guardrails and make ci-local)

Current implementation:
- Detects GROUP BY / SELECT DISTINCT on location.name without shed_id + park co-grouping
- Scans location-display assignments for canonical helper compliance
- Flags new location-bearing tables missing partition_label column

Known blind spots documented in ADR:
- Hardcoded literal strings (Grep required)
- Dynamic composition in application code (code review required)
- Reflective queries built via string concatenation

## How This Achieves the Goal

The convention is now LOCKED via:

1. **Maintainer statement in AGENTS.md** — highest-leverage always-in-context place, with worked examples
2. **Canonical ADR** — complete decision document with evidence, rules, schema requirements, and closure criteria
3. **Do-not-reopen ledger** — documents every defect found, its impact, and closure status (guards against re-litigating the same problems)
4. **Skill updates** — every agent-facing skill that touches location-bearing code now points to the ADR
5. **Subagent brief rule** — AGENTS.md explicitly states: location-bearing work MUST include this rule in the brief
6. **Machine guard** — catches the structural anti-patterns (name-keying, missing partition columns)

A future agent (Claude, Codex, Cursor, or a human) reading AGENTS.md will see the rule immediately, see the worked examples right there, and understand why it's a lock. If they delegate work to a subagent, the rule goes in the brief. If they build location features, they follow the ADR. If they review code, all five skills point them to the canonical source. If they try to hand-roll a location display or group by name, the guard will catch it.

The convention is no longer "stated informally in one place" — it's enforced at five skill entry points, machine-guarded at the gate, and documented with full evidence and worked wrong-examples.
